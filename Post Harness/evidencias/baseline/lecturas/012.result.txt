10: # SharePoint OneDrive integración
11: 
12: ## Qué es
13: 
14: COELSA.Intelligent permite a los usuarios seleccionar archivos corporativos directamente desde **SharePoint** o **OneDrive** usando el **Microsoft File Picker v8**, sin necesidad de descargar y volver a subir el archivo.
15: 
16: ## Cómo funciona
17: 
18: 1. El usuario hace clic en el ícono de SharePoint en el input de chat
19: 2. Se abre el File Picker en un popup/iframe usando la identidad del usuario (OAuth delegado)
20: 3. El usuario selecciona el archivo
21: 4. El backend descarga el archivo usando el token de acceso del usuario con permisos `Files.Read.All`
22: 5. El archivo se procesa como cualquier otro archivo subido (ver [[Flujo de subida de archivos]])
23: 
24: ## Requisitos de configuración
25: 
26: ### Azure AD
27: 
28: La App Registration debe tener el permiso **`Files.Read.All`** (delegado). Este permiso permite leer cualquier archivo del tenant al que el usuario tenga acceso.
29: 
30: ```env
31: SHAREPOINT_CLIENT_ID=<azure-client-id>
32: # Usar el mismo tenant de OAUTH_CLIENT_ID o uno separado
33: ```
34: 
35: ### CSP
36: 
37: El Route de OpenShift debe incluir en `connect-src`:
38: - `login.microsoftonline.com` — para el flujo OAuth del File Picker
39: - `graph.microsoft.com` — para descargar el contenido del archivo
40: 
41: Ver `docs/OPENSHIFT-CONFIGMAP.yaml` para el ejemplo completo.
42:

10: # Validación de urlIdx
11: 
12: ## El problema (upstream bug)
13: 
14: El upstream Open WebUI determinaba el endpoint de un modelo basándose **únicamente** en el campo `owned_by`:
15: - `owned_by == "ollama"` → endpoint nativo de Ollama
16: - Cualquier otro → endpoint OpenAI
17: 
18: **El mismatch**: modelos configurados en LiteLLM con prefijo `ollama/` (ej: `ollama/llama3:70b`) tienen `owned_by=ollama`. El upstream los enviaba al endpoint nativo de Ollama, pero LiteLLM **siempre responde en formato OpenAI**, no en el formato nativo de Ollama. El mismatch de formato generaba **respuestas vacías en la UI**.
19: 
20: ## La corrección
21: 
22: ```python
23: # backend/server/utils/chat.py (líneas ~263–293)
24: # ANTES (upstream):
25: if model.owned_by == "ollama":
26:     endpoint = OLLAMA_BASE_URL
27: 
28: # DESPUÉS (fix COELSA):
29: if model.urlIdx is not None:
30:     # El modelo es proxied (vía LiteLLM o similar) → siempre OpenAI
31:     endpoint = OPENAI_API_BASE_URL
32: elif model.owned_by == "ollama":
33:     # Modelo nativo de Ollama sin proxy
34:     endpoint = OLLAMA_BASE_URL
35: else:
36:     endpoint = OPENAI_API_BASE_URL
37: ```
38: 
39: ## Regla resultante
40: 
41: | Condición | Destino |
42: |-----------|---------|
43: | `urlIdx` definido | LiteLLM proxy (OpenAI endpoint) |
44: | `urlIdx` ausente + `owned_by == "ollama"` | Ollama nativo |
45: | Default | LiteLLM proxy |
46: 
47: ## Relacionado
48:

50: - [[LiteLLM proxy]] — El proxy que siempre responde en formato OpenAI
51: - [[Ollama]] — El servidor nativo que usa su propio formato

9: 
10: # Aislamiento por resource_id
11: 
12: ## Qué es
13: 
14: En el esquema de [[Milvus multi-tenancy|multi-tenancy de Milvus]], el aislamiento entre recursos se logra mediante un campo escalar llamado `resource_id` que se almacena junto a cada vector.
15: 
16: ## Cómo funciona
17: 
18: **Al insertar** un vector (chunk de texto):
19: ```python
20: # Se incluye resource_id en los metadatos del punto
21: {
22:     "vector": [0.1, 0.2, ...],
23:     "resource_id": "knowledge-abc123",
24:     "content": "texto del chunk",
25:     "metadata": {...}
26: }
27: ```
28: 
29: **Al buscar**:
30: ```python
31: # Se aplica un filtro booleano sobre resource_id
32: search_results = collection.search(
33:     data=[query_embedding],
34:     filter=f'resource_id == "{resource_id}"',
35:     ...
36: )
37: ```
38: 
39: Esto garantiza que los resultados de búsqueda pertenecen exclusivamente al recurso solicitado.
40: 
41: ## Por qué es seguro
42: 
43: Milvus ejecuta el filtro booleano en el nivel de cada segmento, antes de devolver resultados. No es posible que un chunk de un `resource_id` diferente aparezca en los resultados de una búsqueda filtrada por otro `resource_id`, siempre que el campo esté indexado correctamente.
44: 
45: ## Cómo se genera el resource_id
46: 
47: El `resource_id` se deriva del identificador del recurso (ID de la Knowledge base, ID del archivo, etc.) mediante una convención de nombres que la función `_get_collection_and_resource_id()` en `milvus_multitenancy.py` implementa.
48:

50: 
51: - [[Milvus multi-tenancy]] — El diseño del que este mecanismo es parte
52: - [[Cinco colecciones Milvus]] — Las colecciones donde se usa resource_id
53: - [[Módulo de retrieval]] — El módulo que aplica los filtros en las búsquedas
54: - [[MOC - RAG y Búsqueda Vectorial]] — Índice del cluster de RAG

9: 
10: # Chats de referencia
11: 
12: ## Qué es
13: 
14: Los **chats de referencia** permiten a los usuarios adjuntar conversaciones previas como contexto extendido al enviar un nuevo mensaje. El chat adjunto se recupera, se formatea y se inyecta en el prompt del modelo junto con el mensaje actual.
15: 
16: ## Cómo se adjunta en el cliente
17: 
18: El chat referenciado viaja como un elemento de tipo `"chat"` dentro del array `files` del payload del socket:
19: 
20: ```json
21: {
22:   "files": [
23:     {
24:       "type": "chat",
25:       "id": "chat-uuid-del-chat-referenciado"
26:     }
27:   ],
28:   "content": "Basándote en la conversación adjunta..."
29: }
30: ```
31: 
32: ## Procesamiento en el backend
33: 
34: En `backend/server/retrieval/utils.py`:
35: 1. Se detecta el elemento `type == "chat"` en `files`
36: 2. Se recupera el chat por ID desde la BD (tabla `chat`)
37: 3. El historial del chat se formatea como bloque Markdown:
38:    ```
39:    ## Conversación de referencia
40:    **Usuario**: ...
41:    **Asistente**: ...
42:    ```
43: 4. El bloque se inyecta al contexto del prompt antes del mensaje del usuario
44: 
45: ## Visibilidad en la UI
46: 
47: La opción de adjuntar chats de referencia aparece en el `InputMenu` y depende del permiso `chat.file_upload` (no del historial local del sidebar). El componente `InputMenu/Chats.svelte` hace su propia llamada a `getChatList` al abrirse, independientemente del estado del sidebar.
48:

50: 
51: - [[Módulo de retrieval]] — El módulo donde se procesa el chat referenciado
52: - [[Grupos y permisos]] — El permiso `chat.file_upload` que controla la visibilidad
