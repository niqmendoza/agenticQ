Empezar por una API y una regla sencilla. Revisar cómo se ejecutan las pruebas hoy, acordar qué resultado se espera y reutilizar los casos existentes. Evaluar primero Schemathesis; sumar Hercules si hace falta recorrer un escenario completo. Para generar y publicar casos, elegir una sola vía.

iTestFlow es candidato para coordinar revisión y Azure. TestForge queda como generador alternativo o experimento hasta aclarar su documentación de licencia. No hace falta encender los cuatro para el piloto.

Las cuatro herramientas, en la práctica

01 · Ejecutar escenarios con IA

TestZeus Hercules

Ollama documentado

Qué hace

Recibe un escenario escrito y usa IA para planificar acciones y operar herramientas de API o navegador.

Cómo ayuda

Puede recorrer un caso de negocio entre varios servicios y conservar evidencia. El plan se estructura en JSON; las herramientas realizan las acciones.

Arquitectura y ejecución oficiales ↗

Cómo usarlo

Transformar el caso aprobado en un escenario Gherkin —pasos “Dado / Cuando / Entonces”—, fijar datos y ambiente, y ejecutarlo desde el runner o pipeline con modelo y herramientas configurados.

Ejemplo simple

Falta un dato obligatorio

Ejecuta un recorrido con ese dato vacío. Comprueba que la solicitud se rechace y que la información guardada siga igual.

Qué falta conectar

Reglas validadas, accesos y limpieza, controles entre servicios, límites del agente, IDs legacy, publicación y asociación de resultados en Azure. La IA consume modelo/GPU también durante la ejecución.

Ver cómo funciona →
Infraestructura, licencia y fuentes

Ruta mínima revisada: 1 contenedor de ejecución

  • Ejecutor Python: lee el escenario, pide decisiones al modelo y guarda resultados/evidencias en archivos. El Dockerfile y el entrypoint incluyen esta ruta.
  • Navegador: instalado en la misma imagen; si hay UI, abre procesos hijos. No se cuenta como otro servicio desplegado. Un navegador remoto sería una alternativa adicional.
  • LLM externo: el modelo que toma decisiones. Se puede evaluar el Ollama existente si responde JSON y llamadas a herramientas correctamente; no confirma compatibilidad con su Qwen concreto.

No se requieren PostgreSQL, MinIO, Redis ni Elasticsearch propios en esta ruta. MCP, consultas SQL, navegador remoto y una interfaz interactiva dependen del uso; no son cuatro servicios obligatorios adicionales. El servidor/API bajo prueba queda fuera del recuento.

Salidas: JUnit, HTML, logs y evidencia según configuración; recogerlos en el pipeline es una conexión a preparar.

02 · Probar contratos de API

Schemathesis

Sin LLM en la base

Qué hace

Lee OpenAPI o GraphQL y genera solicitudes variadas para encontrar respuestas y comportamientos problemáticos.

Cómo ayuda

Amplía la revisión de APIs con límites, entradas inesperadas y secuencias de operaciones. Puede reutilizar IDs obtenidos de respuestas cuando reconoce las conexiones.

Cómo encadena operaciones ↗

Cómo usarlo

Aportar el contrato, configurar autenticación y datos, y ejecutarlo desde el runner existente. Las reglas de negocio específicas se agregan como comprobaciones en código.

Ejemplo simple

Falta un dato obligatorio

Prueba datos ausentes, formatos incorrectos y valores límite. Para comprobar además que nada se modificó, el equipo debe agregar esa regla: el contrato de la API no alcanza.

Qué falta conectar

Checks funcionales entre servicios, preparación/limpieza, pipeline y Azure. Agrupar las variantes generadas bajo casos estables; no crear un caso Azure por cada solicitud aleatoria.

Ver cómo funciona →
Infraestructura, licencia y fuentes

Ruta mínima revisada: 1 ejecutor

  • CLI/Python: proceso que envía solicitudes y verifica resultados. Se puede usar como herramienta local o como un contenedor en un job.
  • Archivos de configuración y reporte: contrato, límites, autenticación por referencias seguras y salidas como JUnit. Son archivos, no servicios nuevos.

La imagen runtime del Dockerfile es una sola imagen de ejecución. Sus etapas de construcción no son servicios permanentes. No necesita navegador, LLM, GPU, PostgreSQL, MinIO, Redis ni Elasticsearch para el recorrido base.

Opcionales: más workers para repartir trabajo; Allure u otro visor de reportes si se elige. Las APIs bajo prueba y el almacenamiento de artefactos del pipeline se cuentan por separado. El Compose de examples/booking es una aplicación de ejemplo, no una dependencia del producto.

03 · Generador alternativo de casos

TestForge

OSS por aclarar

Qué hace

El proyecto de sritajkumarpatel convierte documentos, texto o requisitos de Azure en propuestas de casos mediante agentes.

Cómo ayuda

Acelera el borrador y deja casos estructurados para revisar. Ofrece publicación en Azure por PAT o mediante una sesión de navegador.

Proyecto exacto y flujo documentado ↗

Cómo usarlo

Darle documentación funcional validada y una muestra de casos legacy. Revisar la salida JSON antes de publicarla. En el escenario conjunto, exportar propuestas a la única vía de aprobación/publicación mediante un puente por construir.

Ejemplo simple

Proponer un caso

Propone probar qué ocurre cuando falta un dato obligatorio. QA revisa si el caso ya existe antes de agregarlo.

Qué falta conectar

Recuperación desde RAGFlow, comparación y actualización legacy, fuentes/versiones, código ejecutable y runner. Sus logs y “pipeline” corresponden a generación de casos; no demuestran una prueba ejecutada sobre la aplicación.

Ver cómo funciona →
Infraestructura, confirmación OSS y fuentes

Ruta mínima revisada: 1 contenedor de aplicación

  • Servidor Node + interfaz React: una aplicación desplegada; el servidor sirve la web ya construida. No son dos contenedores en el Compose de producción.
  • Volumen de logs: conserva registros como archivos. No es una base de datos ni un servicio adicional.
  • LLM externo: Ollama está implementado como proveedor. Se puede apuntar al servidor existente; la calidad del Qwen exacto sigue por probar.

El Compose activa solo testforge. Ollama aparece comentado como sidecar opcional: sería un contenedor adicional si se lo desplegara ahí, pero no hace falta duplicar el que ya tienen. No hay PostgreSQL, MinIO, Redis ni Elasticsearch obligatorios en esta base.

Navegador opcional: para publicación con CDP se necesita una sesión Chrome/Edge accesible. Con PAT puede evitarse ese camino. En desarrollo web y servidor pueden correr separados; ese recuento no se mezcla con producción.

04 · Revisar y publicar con QA

iTestFlow

Ollama por probar/adaptar

Qué hace

Reúne conocimiento, análisis de requisitos, diseño y revisión de casos, cobertura y publicación en Azure.

Cómo ayuda

Tiene pasos de revisión humana y casos editables. El código de publicación crea casos, vincula la historia de usuario y los incorpora a una suite elegida o basada en requisito.

Publicación aprobada en Azure ↗

Cómo usarlo

Configurar proyecto, accesos y modelo; aportar fuentes validadas y contrastar cobertura legacy. QA edita y aprueba. La ejecución actual contempla Playwright MCP y código de herramientas HTTP/DB con comprobaciones explícitas; no se ejecutó aquí.

Ejemplo simple

Revisar un caso existente

Si un caso ya comprueba el rechazo, señala que quizá falta verificar que no se modificó la información guardada. QA decide si completa ese caso, sin duplicarlo.

Qué falta conectar

Consulta a RAGFlow, sincronización de fuentes/versiones y actualización segura de IDs legacy. Integrar resultados externos de Schemathesis/Hercules y probar el circuito real de ejecución, publicación y reejecución.

Ver cómo funciona →
Infraestructura, alcance API y fuentes

Ruta mínima revisada: 3 componentes ejecutables

  • Aplicación web Node 24+: interfaz y API del sistema en un mismo componente Next.js. No contar frontend y backend como dos servicios desplegados independientes.
  • Worker: proceso que realiza tareas en segundo plano. El comando de inicio supervisa web y worker; un comando no significa un solo proceso de trabajo.
  • PostgreSQL 16: guarda trabajo, contexto, historial y tareas. Puede ser una base propia en contenedor o una instancia ya disponible.

El Compose incluido levanta 1 contenedor por defecto: PostgreSQL; la web y el worker corren con npm. No es un despliegue completo de tres contenedores. Perfiles opcionales: postgres-test para pruebas de integración y pgadmin para administrar la base; suman hasta dos contenedores de apoyo, no obligatorios.

Exterior: Azure y proveedor LLM. Para UI, Playwright MCP y navegador son componentes de ejecución adicionales o reutilizados si son compatibles. No hay MinIO, Redis ni Elasticsearch obligatorios en el Compose revisado; los datos se guardan en PostgreSQL y la evidencia requiere verificar su configuración.

Componente transversal existente

RAGFlow: consultar lo que ya saben

RAGFlow ya está en su infraestructura, según el relato actual. Puede ayudar a recuperar notas y documentos para responder preguntas y preparar casos. No reemplaza a ninguno de los cuatro softwares.

Ver diagrama Git / RAGFlow →

Propuesta: conservar notas y documentación validada en Git; sincronizar esa revisión a RAGFlow con aplicación, versión, estado y commit como metadatos. Consultar directamente allí y conservar las fuentes recuperadas.

Configuración de metadatos y recuperación ↗

Git conserva historia y revisiones. La revisión humana determina qué queda aprobado. RAGFlow mantiene una copia preparada para búsqueda; hay que diseñar sincronización y filtros. No se verificó un control de versiones equivalente a Git.

Leer código sirve para documentar comportamiento técnico. Para evitar repetir un bug en documentos y tests, negocio/producto debe confirmar el esperado de forma independiente. Contradicciones entre notas, código, contrato y legacy quedan como preguntas.

Pendiente: inventario de la versión/perfiles desplegados de RAGFlow, permisos, modelo de búsqueda, filtros y acceso por API. No se inspeccionó su instalación.

Infraestructura RAGFlow: referencia concreta, sin sumarla como nueva

Referencia revisada: main en commit 2400ca8, Compose CPU y .env sin overrides: motor Elasticsearch, metadatos MySQL y perfiles Go/ClickHouse. El archivo fija imagen v1.0.0-rc1. Es una referencia de lectura, no una recomendación de migración ni la versión instalada.

7 servicios definidos activos en ese recuento: ragflow-cpu, es01, mysql, minio, kvrocks, nats y clickhouse. Cuenta entradas activas de los dos Compose incluidos según sus perfiles; no procesos internos, volúmenes, modelo externo ni contenedores realmente arrancados. No se ejecutó Compose.

  • RAGFlow: interfaz, API y trabajo interno para cargar y consultar documentos.
  • Elasticsearch: índice para encontrar fragmentos de información.
  • MySQL: datos de administración y metadatos del producto.
  • Almacenamiento de archivos: el servicio se llama minio, pero en esta referencia usa imagen pgsty/silo; no asumir la imagen histórica de MinIO.
  • Kvrocks y NATS: estado y mensajería/tareas para la ruta Go. No equipararlos automáticamente a un stack histórico Redis.
  • ClickHouse: almacenamiento analítico, presente en los perfiles de esta referencia.

Alternativas y opcionales: OpenSearch, Infinity, SereneDB, Oceanbase o Seekdb son perfiles de motor alternativo; no se suman todos al mismo despliegue. TEI CPU/GPU puede servir modelos que convierten texto en vectores de búsqueda. Sandbox, Jaeger y Kibana son apoyos opcionales. La selección de perfiles y versión cambia el recuento.

Ejemplo con las cuatro · diseño por construir

Un lote adicional, una sola aprobación y dos tipos de prueba

  1. RAGFlow devuelve una regla funcional aprobada, sus fuentes y la revisión de Git.
  2. TestForge, condicionado a aclarar su licencia, propone un lote pequeño de variantes faltantes. No vuelve a generar todos los casos que ya cubre el legacy.
  3. Un puente por construir normaliza las propuestas para iTestFlow. QA las contrasta con legacy y aprueba; esa única vía publica casos nuevos justificados o actualiza IDs con la reconciliación diseñada. La ingestión TestForge → iTestFlow no se verificó como función nativa.
  4. Schemathesis prueba el contrato y las comprobaciones funcionales escritas. Hercules recorre un escenario de punta a punta y comprueba el resultado esperado.
  5. QA consolida evidencia y valida la clasificación. El colector futuro asocia resultados en Azure y produce Markdown con defectos confirmados para desarrollo.
  6. Desarrollo y Copilot reproducen y corrigen; el runner reejecuta y QA verifica el cierre. Si todo es conforme, se registra el resultado sin inventar un defecto.

Este ejemplo explica cómo combinar las cuatro técnicamente. Para el primer piloto, usar menos piezas y medir cada incorporación; los puentes y la actualización segura del legacy siguen pendientes.

Un único responsable de Azure

Propuesta: iTestFlow como vía única de revisión y publicación. TestForge puede generar una alternativa sobre una muestra; un puente debe normalizar su JSON para el mismo circuito, sin publicar por duplicado ni obligar a doble generación.

Antes de escribir, recuperar legacy y decidir conservar / actualizar / crear. Mantener un mapa de IDs y un registro de operaciones para que repetir la solicitud no vuelva a crear casos. La función revisada de iTestFlow crea casos nuevos; la reconciliación y actualización del legacy necesitan diseño y verificación.

El coordinador puede empezar siendo una persona con pasos documentados. Un script o n8n/IBM se evalúa más adelante; no es dependencia del piloto.

Puentes que hay que construir

  • Sincronización Git → RAGFlow y consulta con revisión/fuentes identificadas.
  • RAGFlow + exportación legacy → propuestas del generador elegido.
  • Casos aprobados → código/escenario revisado → runner actual.
  • Resultados externos → evidencia → asociación de prueba/caso/requisito en Azure.
  • Hallazgo validado → Markdown para desarrollo → reejecución y cierre.

API o MCP son vías de integración. MCP expone herramientas; no sustituye modelo ni runner. Catálogo y permisos reales deben verificarse.

Primer piloto: un recorrido que se pueda comprobar

  1. Entender y acordar

    Observar una prueba manual y una automática. Elegir una API, definir una regla sencilla y acordar los datos, la preparación y quién confirma el resultado esperado.

  2. Probar pocas piezas

    Reutilizar RAGFlow y legacy. Schemathesis para contrato + checks funcionales; un escenario Hercules si aporta valor. Elegir un generador/publicador después de verificar licencia y modelo.

  3. Seguir hasta el cierre

    Mostrar caso → código → corrida → evidencia → resultado asociado en Azure. Validar un hallazgo, entregar Markdown a desarrollo y comprobar la reejecución. Si no hay defecto, registrar conformidad con evidencia.
