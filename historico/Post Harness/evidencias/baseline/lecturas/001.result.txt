10: # Borrado en cascada de archivos
11: 
12: ## Qué es
13: 
14: Cuando un usuario **elimina una conversación (chat)**, COELSA.Intelligent elimina automáticamente todos los archivos asociados a esa conversación, tanto en la base de datos como en [[MinIO S3]].
15: 
16: ## Por qué existe
17: 
18: Sin esta funcionalidad, eliminar un chat dejaría archivos huérfanos en MinIO indefinidamente. A largo plazo, esto genera acumulación de storage sin posibilidad de recuperarlo sin una migración manual.
19: 
20: ## Implementación
21: 
22: El modelo `File` tiene una columna `chat_id` (con índice):
23: 
24: ```python
25: class File(Base):
26:     chat_id = Column(String, nullable=True, index=True)
27:     # Vinculación con chats para borrado en cascada
28: ```
29: 
30: Cuando el endpoint de eliminación de chat se ejecuta:
31: 1. Busca todos los registros `File` donde `chat_id == chat.id`
32: 2. Para cada archivo: llama a `StorageProvider.delete_file(file.path)`
33: 3. Elimina los registros de la tabla `file`
34: 4. Elimina el registro del chat
35: 
36: ## Diferencia con el Scheduler
37: 
38: | Mecanismo | Cuándo actúa | Qué elimina |
39: |-----------|-------------|-------------|
40: | **Borrado en cascada** | Al eliminar un chat | Archivos del chat eliminado |
41: | **[[Scheduler de limpieza]]** | Diariamente | Huérfanos + archivos vencidos |
42: 
43: Ambos mecanismos son complementarios.
44:

46:

49: - [[MinIO S3]] — El storage donde se eliminan los objetos
50: - [[MOC - Almacenamiento]] — Índice del cluster de almacenamiento

10: # Flujo de subida de archivos
11: 
12: ## Qué es
13: 
14: Describe el ciclo completo desde que un usuario sube un archivo hasta que queda accesible via URL firmada en MinIO.
15: 
16: ## Pasos del flujo
17: 
18: ### 1. Recepción (router `files.py`)
19: El endpoint `POST /api/v1/files/` recibe el archivo multipart. El backend:
20: - Sanitiza el nombre del archivo (protección contra [[Path Traversal]])
21: - Guarda temporalmente en `data/uploads/<uuid>-<filename>`
22: - Crea un registro en la tabla `file` con `path` = ruta local
23: 
24: ### 2. Procesamiento RAG (opcional)
25: Si el archivo va a ser embedido (Knowledge base, búsqueda vectorial):
26: - Se procesa con los loaders del [[Módulo de retrieval]]
27: - Los chunks se insertan en [[Milvus]] bajo la colección correspondiente
28: 
29: ### 3. Migración a MinIO (scheduler diario)
30: El [[Scheduler de limpieza|scheduler]] ejecuta diariamente:
31: - Lee los registros de `file` con `path` local
32: - Sube cada archivo a [[MinIO S3]]
33: - Actualiza el campo `path` en BD con la clave S3
34: - Genera una [[URLs firmadas MinIO|URL firmada]] para el acceso
35: 
36: ### 4. Acceso
37: Al solicitar un archivo, el backend:
38: - Verifica [[Control de acceso a recursos|access_control]]
39: - Si el path es S3: genera una URL firmada con expiración configurable
40: - Si el path es local: sirve el archivo directamente
41: 
42: ## Relacionado
43: 
44: - [[Sistema híbrido de almacenamiento]] — El modelo general del que este flujo es parte
45: - [[URLs firmadas MinIO]] — Cómo se generan las URLs de acceso
46: - [[Scheduler de limpieza]] — El job que ejecuta la migración y la limpieza
47: - [[Borrado en cascada de archivos]] — Qué pasa cuando se elimina el chat asociado
48: - [[Protección SSRF]] — La sanitización de paths en el paso de recepción

10: # Scheduler de limpieza
11: 
12: ## Qué es
13: 
14: COELSA.Intelligent tiene un **scheduler que corre diariamente** y realiza dos tareas sobre el almacenamiento:
15: 1. **Migra** archivos desde almacenamiento local a [[MinIO S3]]
16: 2. **Elimina** archivos huérfanos (sin registro en BD) y archivos que superan el umbral de antigüedad
17: 
18: ## Configuración
19: 
20: ```env
21: FILE_STORAGE_CLEANUP_DAYS=30
22: ```
23: 
24: Con este valor, los archivos que no han sido accedidos en más de 30 días son candidatos para eliminación. El campo `last_accessed_at` del modelo `File` registra el último acceso.
25: 
26: ## Qué es un archivo huérfano
27: 
28: Un archivo **huérfano** es aquel que:
29: - Existe físicamente en el almacenamiento (local o MinIO)
30: - **No tiene** un registro correspondiente en la tabla `file` de la base de datos
31: 
32: Esto puede ocurrir si un upload falló a medias o si un registro fue eliminado manualmente de la BD sin limpiar el storage.
33: 
34: ## Cuándo se ejecuta
35: 
36: El scheduler es un job asíncrono que se registra durante el `lifespan` de la aplicación FastAPI. No tiene una hora fija; se ejecuta cada 24 horas a partir del arranque del servidor.
37:

10: # Sistema híbrido de almacenamiento
11: 
12: ## Qué es
13: 
14: El almacenamiento de archivos en COELSA.Intelligent opera en modo **híbrido**: los archivos se reciben localmente y luego se migran a [[MinIO S3]]. Los archivos viejos y los nuevos coexisten hasta que el scheduler los migra.
15: 
16: ## Flujo completo
17: 
18: ```
19: Usuario sube archivo
20:        ↓
21: Backend guarda en data/uploads/ (local temporal)
22:        ↓
23: [Scheduler diario] detecta archivos locales
24:        ↓
25: Migra a MinIO → genera presigned URL
26:        ↓
27: Actualiza metadatos en BD (path = s3://bucket/key)
28:        ↓
29: [Acceso futuro] devuelve URL firmada de MinIO
30: ```
31: 
32: ## Proveedores disponibles
33: 
34: La interfaz `StorageProvider` (en `backend/server/storage/provider.py`) es abstracta. Las implementaciones concretas son:
35: - `LocalStorageProvider` — guarda en `data/uploads/`
36: - `S3StorageProvider` (MinIO / AWS S3)
37: - `GCSStorageProvider` (Google Cloud Storage)
38: - `AzureBlobStorageProvider` (Azure Blob Storage)
39: 
40: La variable `STORAGE_PROVIDER` en `.env` selecciona el provider activo.
41: 
42: ## Fallback local
43: 
44: Si MinIO no está disponible, el sistema usa el almacenamiento local. Esto permite desarrollo local sin configurar MinIO, aunque los archivos no persisten en caso de recreación del contenedor.
45: 
46: ## Script de migración
47: 
48: Para migrar archivos existentes a MinIO en un entorno ya en producción:
49: 
50: ```bash
51: python scripts/migrate_to_minio.py
52: ```
53:

59: - [[Scheduler de limpieza]] — El job que limpia archivos vencidos

10: # Storage Dashboard
11: 
12: ## Qué es
13: 
14: El **Storage Dashboard** es un conjunto de endpoints de monitoreo que expone métricas de uso del almacenamiento de COELSA.Intelligent. Requiere rol `admin`.
15: 
16: ## Endpoints
17: 
18: ```
19: GET /api/v1/storage/status
20: ```
21: 
22: Retorna:
23: - Espacio total y usado en MinIO
24: - Número de objetos en el bucket
25: - Número de archivos registrados en la BD
26: - Archivos locales pendientes de migración
27: - Archivos huérfanos detectados
28: - Estadísticas de antigüedad de archivos
29: 
30: ## Router
31: 
32: El router está en `backend/server/routers/storage_management.py`. Los endpoints delegan a `StorageProvider.get_storage_stats()` para obtener las métricas del provider activo.
33: 
34: ## Acceso
35: 
36: Solo usuarios con rol `admin` pueden acceder a estos endpoints. Un usuario con rol `user` recibirá un error `403 Forbidden`. Ver [[Roles de usuario]].
37:
