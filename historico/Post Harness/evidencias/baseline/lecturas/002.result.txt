10: # URLs firmadas MinIO
11: 
12: ## Qué es
13: 
14: Las **URLs firmadas** (presigned URLs) son URLs de acceso temporal a objetos en [[MinIO S3]] que no requieren que el cliente tenga credenciales del bucket. El servidor firma la URL con las credenciales S3 y establece un tiempo de expiración.
15: 
16: ## Cómo funciona
17: 
18: ```python
19: # Pseudocódigo de generación (StorageProvider.get_presigned_url)
20: url = s3_client.generate_presigned_url(
21:     'get_object',
22:     Params={'Bucket': S3_BUCKET_NAME, 'Key': file_path},
23:     ExpiresIn=3600  # 1 hora por defecto
24: )
25: ```
26: 
27: La URL resultante incluye la firma criptográfica y la fecha de expiración en los query params. Solo es válida hasta esa fecha y solo para el objeto específico.
28: 
29: ## Por qué URLs firmadas
30: 
31: - **Seguridad**: el cliente nunca recibe credenciales del bucket; solo puede acceder al archivo específico por el tiempo configurado
32: - **Control de acceso**: si el [[Control de acceso a recursos|access_control]] del archivo cambia, las URLs viejas siguen siendo válidas hasta su expiración pero no se generan nuevas
33: - **Descarga directa**: el cliente descarga directo de MinIO sin pasar por el backend, reduciendo la carga del servidor
34: 
35: ## Configuración de expiración
36: 
37: La expiración por defecto es **3600 segundos (1 hora)**. El parámetro `ExpiresIn` es configurable en la llamada a `get_presigned_url()`.
38: 
39: ## Timeouts boto3 (Windows)
40: 
41: Para evitar timeouts en entornos Windows con latencia de red:
42: - Connect timeout: 30s
43: - Read timeout: 120s
44: - 10 reintentos con backoff exponencial
45: - TCP keepalive habilitado
46:

10: # Fork de Open WebUI
11: 
12: ## Qué es
13: 
14: COELSA.Intelligent es un fork interno de [Open WebUI](https://github.com/open-webui/open-webui), una plataforma de chat con IA generativa de código abierto (licencia MIT). El fork se tomó sobre una versión base estabilizada y los cambios se aplican deliberadamente sobre esa base.
15: 
16: **No se mantiene compatibilidad directa con el upstream.** Esto significa que las actualizaciones del proyecto original no se incorporan automáticamente; cualquier cambio relevante del upstream debe evaluarse y portarse manualmente.
17: 
18: ## Qué cambia respecto al upstream
19: 
20: | Área | Upstream (Open WebUI) | COELSA.Intelligent |
21: |------|----------------------|-------------------|
22: | Base de datos | SQLite (default) | [[PostgreSQL]] |
23: | Autenticación | Múltiples proveedores + registro local | Solo [[Azure AD OAuth]] |
24: | Almacenamiento | Local (`data/uploads/`) | Híbrido local + [[MinIO S3]] |
25: | Búsqueda vectorial | Una colección por recurso | [[Milvus multi-tenancy]] (5 colecciones) |
26: | Identidad visual | Open WebUI branding | [[ECO Design System]] COELSA |
27: | Idioma por defecto | `en-US` | `es-AR` |
28: | Despliegue | Docker genérico | [[OpenShift]] + Azure DevOps |
29: 
30: ## Por qué no se sigue el upstream
31: 
32: El upstream evoluciona rápido y no está optimizado para las restricciones corporativas de COELSA (Azure AD, OpenShift, proxy corporativo, identidad visual propia). Mantener sincronización con el upstream requeriría resolver conflictos continuamente en áreas que COELSA deliberadamente modificó. La decisión es mantener una versión estabilizada y hacer cherry-pick de mejoras puntuales cuando sea necesario.
33:

9: 
10: # Headers de usuario COELSA
11: 
12: ## Qué es
13: 
14: COELSA.Intelligent renombró los encabezados HTTP que propagan la identidad del usuario autenticado entre componentes. La convención es:
15: 
16: ```
17: X-COELSA.Intelligent-User-*
18: ```
19: 
20: Estos headers viajan en las requests del proxy y del middleware de autenticación hacia los servicios internos.
21: 
22: ## Por qué el renombre
23: 
24: El upstream Open WebUI usaba nombres de header genéricos. El renombre hace que el origen de los headers sea inequívoco en logs y en reglas de seguridad de red, y evita colisiones con otros sistemas que puedan pasar headers similares.
25: 
26: ## Uso
27: 
28: Los headers se inyectan automáticamente por el middleware de autenticación al validar el token JWT. Los routers que necesitan la identidad del usuario usan el sistema estándar de dependencias de FastAPI (`get_current_user`) en lugar de leer los headers directamente.
29: 
30: ## Relacionado
31:

33: - [[FastAPI y uvicorn]] — El servidor donde el middleware de auth corre
34: - [[Azure AD login exclusivo]] — La fuente de identidad que genera estos headers
35: - [[MOC - Arquitectura]] — Contexto de la convención en el sistema

9: 
10: # PostgreSQL como base de datos
11: 
12: ## Qué es
13: 
14: El upstream Open WebUI usa SQLite por defecto. COELSA.Intelligent **migró a PostgreSQL** para soportar múltiples workers concurrentes, backups corporativos y el modelo de despliegue en [[OpenShift]].
15: 
16: ## Configuración
17: 
18: ```env
19: DATABASE_URL=postgresql://user:pass@host:5432/coelsa_intelligent
20: ```
21: 
22: El esquema se gestiona con **Alembic**. Las migraciones están en `backend/server/migrations/`. El servidor ejecuta `alembic upgrade head` automáticamente al arrancar (via `run_migrations()` en `config.py`).
23: 
24: ## Por qué PostgreSQL
25: 
26: - SQLite no admite múltiples writers concurrentes; con uvicorn en múltiples workers genera errores de lock.
27: - PostgreSQL tiene soporte corporativo, backup integrado con las herramientas de COELSA, y funcionalidades como JSON columns (usadas en varios modelos).
28: - La versión mínima requerida es **14+** por el uso de `json_agg` y funciones de ventana.
29: 
30: ## Stack de acceso a datos
31: 
32: - **ORM**: SQLAlchemy (con `get_db()` como context manager de sesión)
33: - **Migraciones**: Alembic (ver [[Migraciones Alembic]])
34: - **Modelos**: `backend/server/models/` — User, Chat, File, Knowledge, Group, Memory, etc.
35:
