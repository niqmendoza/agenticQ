10: # Despliegue en OpenShift
11: 
12: ## Pasos de despliegue
13: 
14: ### Prerequisitos (primera vez)
15: 
16: 1. **Crear el bucket MinIO**:
17:    ```bash
18:    python scripts/create_minio_bucket.py
19:    ```
20:    Requiere que las variables `S3_*` estén en `.env`.
21: 
22: 2. **Aplicar ConfigMap** con variables de entorno:
23:    ```bash
24:    oc apply -f docs/OPENSHIFT-CONFIGMAP.yaml
25:    ```
26: 
27: 3. **Aplicar configuración de Routes** (incluye CSP):
28:    ```bash
29:    oc apply -f docs/OPENSHIFT-ROUTE-CONFIG.yaml
30:    ```
31: 
32: ### Deploy de una nueva versión
33: 
34: Ejecutar el pipeline correspondiente:
35: - **DEV**: `azure-pipeline-DEV.yml`
36: - **VALIDACION**: `azure-pipeline-VALIDACION.yml`
37: - **PRODUCCIÓN**: `azure-pipeline-PROD.yml`
38: 
39: ### Migraciones de base de datos
40: 
41: ```bash
42: cd backend
43: alembic upgrade head
44: ```
45: 
46: El servidor aplica migraciones automáticamente al arrancar. Si hay migraciones pendientes críticas, ejecutarlas manualmente antes del deploy.
47: 
48: ## Configuración crítica del Route
49: 
50: ### Timeout de HAProxy
51: 
52: El timeout de HAProxy en el Route **debe ser mayor a 300 segundos**. El procesamiento de archivos con RAG (embedding + inserción en Milvus) puede superar 5 minutos en documentos grandes.
53: 
54: ```yaml
55: # En la anotación del Route de OpenShift
56: haproxy.router.openshift.io/timeout: 600s
57: ```
58: 
59: ### CSP para SharePoint
60: 
61: Si [[SharePoint OneDrive integración]] está activo, incluir en la CSP:
62: ```
63: connect-src: login.microsoftonline.com graph.microsoft.com
64: ```

10: # Dockerfile
11: 
12: ## Qué es
13: 
14: El `Dockerfile` en la raíz del proyecto construye la imagen de producción de COELSA.Intelligent. Combina el build del frontend estático con el backend Python en una sola imagen.
15: 
16: ## Características clave
17: 
18: ### PyTorch CPU-only
19: 
20: ```dockerfile
21: RUN pip3 install torch==2.5.1+cpu \
22:     --index-url https://download.pytorch.org/whl/cpu
23: ```
24: 
25: La variante CUDA (~2GB) no se usa porque [[OpenShift]] no tiene GPUs disponibles. Ver [[PyTorch CPU-only]].
26: 
27: ### Sin Pyodide
28: 
29: El build usa `npm run build:docker` (no `npm run build`), que **no descarga Pyodide**. Ver [[Build frontend]].
30: 
31: ### SSL corporativo (riesgo aceptado)
32: 
33: ```dockerfile
34: ENV NODE_TLS_REJECT_UNAUTHORIZED=0
35: ENV npm_config_strict_ssl=false
36: ENV PIP_TRUSTED_HOST="download.pytorch.org pypi.org files.pythonhosted.org"
37: ```
38: 
39: Estas variables deshabilitan la verificación SSL en `npm` y `pip` durante el build. Necesario en el entorno de CI/CD con proxy corporativo que intercepta HTTPS. Ver [[SSL corporativo en build]] y [[Riesgos de seguridad aceptados]].
40: 
41: ### CHANGELOG en la ruta correcta
42: 
43: ```dockerfile
44: COPY CHANGELOG.md /app/CHANGELOG.md
45: ```
46: 
47: Corrección del v1.3.0: anteriormente se copiaba a `/app/backend/CHANGELOG.md` pero la app lo buscaba en `/app/CHANGELOG.md`.
48:

10: # Pipelines Azure DevOps
11: 
12: ## Qué es
13: 
14: COELSA.Intelligent tiene **4 pipelines de Azure DevOps** que gestionan el ciclo de vida completo desde el commit hasta producción.
15: 
16: ## Los 4 pipelines
17: 
18: | Archivo | Entorno | Propósito |
19: |---------|---------|-----------|
20: | `azure-pipeline-DEV.yml` | DEV | Build y deploy automático de ramas de feature |
21: | `azure-pipeline-VALIDACION.yml` | VALIDACION | Build y deploy para QA/testing |
22: | `azure-pipeline-PROD.yml` | PRODUCCIÓN | Deploy a producción (requiere aprobación) |
23: | `azure-pipeline-RELEASE.yml` | — | Gestión de versiones (tagging, changelogs) |
24: 
25: ## Pasos típicos de un pipeline
26: 
27: 1. **Build frontend**: `npm run build:docker` (sin Pyodide — ver [[Build frontend]])
28: 2. **Build imagen Docker**: `docker build -t ...` (ver [[Dockerfile]])
29: 3. **Push a registry**: push de la imagen al registro corporativo
30: 4. **Deploy a OpenShift**: `oc apply` con la nueva imagen
31: 
32: ## Variables críticas de entorno en los pipelines
33: 
34: Las variables de entorno de la app **no** están hardcodeadas en los pipelines. Se inyectan desde:
35: - **ConfigMap de OpenShift**: variables de aplicación — ver [[Despliegue en OpenShift]]
36: - **Azure DevOps Variable Groups**: credenciales (secrets) del pipeline
37:

9: 
10: # SSL corporativo en build
11: 
12: ## Qué es
13: 
14: El Dockerfile de COELSA.Intelligent tiene la verificación SSL deshabilitada en los pasos de instalación de dependencias:
15: 
16: ```dockerfile
17: ENV NODE_TLS_REJECT_UNAUTHORIZED=0
18: ENV npm_config_strict_ssl=false
19: ENV PIP_TRUSTED_HOST="download.pytorch.org download-r2.pytorch.org pypi.org files.pythonhosted.org"
20: ```
21: 
22: ## Por qué está deshabilitado
23: 
24: El entorno de CI/CD de COELSA tiene un **proxy corporativo** que intercepta el tráfico HTTPS y lo re-encripta con sus propios certificados TLS. Estos certificados son de la CA corporativa de COELSA, que **no está instalada en las imágenes base** de Docker usadas en el pipeline.
25: 
26: Resultado: `npm` y `pip` ven certificados que no reconocen → error de SSL → fallo del build.
27: 
28: La deshabilitación de SSL es el workaround temporal mientras se resuelve la instalación de los CAs corporativos a nivel de imagen base.
29: 
30: ## El riesgo
31: 
32: Con SSL deshabilitado, `npm` y `pip` **no verifican la autenticidad del servidor** durante la descarga de dependencias. Un atacante con posición de man-in-the-middle en la red corporativa podría inyectar paquetes maliciosos.
33: 
34: Este es un **riesgo aceptado** documentado en [[Riesgos de seguridad aceptados]].
35: 
36: ## La solución correcta
37: 
38: 1. Instalar los certificados CA corporativos en la imagen base de Docker
39: 2. Eliminar las variables `NODE_TLS_REJECT_UNAUTHORIZED`, `npm_config_strict_ssl` y `PIP_TRUSTED_HOST` del Dockerfile
40: 
41: Esta solución requiere coordinación con el equipo de infraestructura de COELSA.
42:

10: # COELSA.Intelligent — Home
11: 
12: Plataforma interna de chat con IA generativa de COELSA. Fork de Open WebUI adaptado para infraestructura corporativa: autenticación Azure AD, almacenamiento MinIO/S3, búsqueda vectorial Milvus, identidad visual COELSA y despliegue en OpenShift.
13: 
14: **Versión actual:** v1.3.0
15: **Entornos activos:** DEV · VALIDACION · PRODUCCIÓN (OpenShift)
16: **Repo base:** Fork de Open WebUI (MIT); cambios aplicados sobre versión estabilizada sin seguimiento del upstream.
17: 
18: > **Para LLMs:** cada nota tiene un campo `description` tipo "Usar cuando…" en el frontmatter YAML. Leer ese campo es suficiente para saber si la nota es relevante antes de leer el cuerpo completo.

23: 
24: ## Invariantes del proyecto (reglas que nunca se rompen)
25: 
26: - La autenticación es **exclusivamente Azure AD**; el registro local y el formulario de login están deshabilitados.
27: - **Teal (`#06ABB9`) es el color primario COELSA** en ambos temas (light y dark). Pink es solo acento decorativo.
28: - SSR está deshabilitado (`export const ssr = false`); la app es una SPA pura.
29: - No se mantiene compatibilidad directa con el upstream Open WebUI; los cambios se aplican deliberadamente.
30: - Todo par texto/fondo debe cumplir WCAG AA (4.5:1 texto normal, 3:1 texto grande).
31: - No hardcodear valores hex en componentes; usar siempre roles/tokens semánticos del ECO Design System.
