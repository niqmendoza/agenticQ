10: # Cadena SearXNG Context Forge
11: 
12: ## Qué es
13: 
14: La integración de búsqueda web en COELSA.Intelligent usa una cadena de 4 componentes:
15: 
16: ```
17: Open WebUI → MCPO (puerto 8000) → Context Forge (puerto 4444) → searxng-mcp → SearXNG
18: ```
19: 
20: ## Componentes
21: 
22: | Componente | Puerto | Rol |
23: |-----------|--------|-----|
24: | **MCPO** | 8000 | Proxy MCP → HTTP que convierte el protocolo MCP a una API HTTP/OpenAPI |
25: | **Context Forge** | 4444 | Orquestador de contexto; registra herramientas MCP y las expone via OpenAPI |
26: | **searxng-mcp** | — | Servidor MCP que envuelve SearXNG con el protocolo MCP |
27: | **SearXNG** | — | Motor de búsqueda metasearch (privado, self-hosted) |
28: 
29: ## Por qué esta cadena
30: 
31: - SearXNG es self-hosted para mantener privacidad (sin tracking de búsquedas)
32: - MCP es el protocolo estándar para tool calling en agentes IA
33: - MCPO convierte MCP a HTTP/OpenAPI, que es lo que Open WebUI entiende como tool server
34: 
35: ## Configuración
36: 
37: ```env
38: TOOL_SERVER_CONNECTIONS=[
39:   {
40:     "url": "http://host:8000/contextforge",
41:     "path": "openapi.json",
42:     "auth_type": "bearer",
43:     "key": "tu-api-key"
44:   }
45: ]
46: ```
47: 
48: ## Relación con non-native function calling
49: 
50: Para el modelo `gpt-oss:120b` (sin function calling nativo), la herramienta se describe en el system prompt. Ver [[MCP y tool calling]] para el detalle del JSON prompt.
51:

9: 
10: # MCP y tool calling
11: 
12: ## Qué es
13: 
14: COELSA.Intelligent integra **Model Context Protocol (MCP)** para exponer herramientas (tools) a los modelos. La herramienta principal configurada es [[Cadena SearXNG Context Forge|búsqueda web via SearXNG]].
15: 
16: ## Dos modos de tool calling
17: 
18: ### 1. Native function calling
19: Modelos que soportan function calling nativo (formato OpenAI `tools`). El backend envía las herramientas disponibles en el payload y el modelo responde con llamadas estructuradas.
20: 
21: ### 2. Non-native function calling (JSON prompt)
22: El modelo `gpt-oss:120b` **no soporta tool calling nativo de forma confiable**. COELSA.Intelligent implementa un workaround:
23: 
24: 1. Las herramientas disponibles se describen en el **system prompt** como JSON
25: 2. Se le indica al modelo que responda con un JSON específico cuando quiera llamar una herramienta
26: 3. El backend parsea la respuesta del modelo buscando el JSON de tool call
27: 4. Ejecuta la herramienta y vuelve a llamar al modelo con el resultado
28: 
29: ## Parsing robusto de JSON
30: 
31: Los modelos grandes frecuentemente incluyen texto adicional antes o después del JSON válido. El parser usa `json.JSONDecoder().raw_decode()` para tolerar este "ruido":
32: 
33: ```python
34: # backend/server/utils/middleware.py
35: decoder = json.JSONDecoder()
36: obj, end_idx = decoder.raw_decode(model_response)
37: # obj es el JSON válido; el texto después de end_idx se descarta
38: ```
39: 
40: ## Configuración
41: 
42: ```env
43: TOOL_SERVER_CONNECTIONS=[
44:   {
45:     "url": "http://host:8000/contextforge",
46:     "path": "openapi.json",
47:     "auth_type": "bearer",
48:     "key": "..."
49:   }
50: ]
51: ```

9: 
10: # PyTorch CPU-only
11: 
12: ## Qué es
13: 
14: El [[Dockerfile]] de COELSA.Intelligent instala **PyTorch en su variante CPU-only** en lugar de la variante con soporte CUDA (GPU):
15: 
16: ```dockerfile
17: RUN pip3 install torch==2.5.1+cpu \
18:     --index-url https://download.pytorch.org/whl/cpu
19: ```
20: 
21: ## Por qué CPU-only
22: 
23: | Variante | Tamaño | Requisito |
24: |----------|--------|-----------|
25: | CUDA | ~2GB | GPU NVIDIA en el nodo |
26: | CPU-only | ~200MB | Solo CPU |
27: 
28: Los contenedores en [[OpenShift]] de COELSA **no tienen acceso a GPU**. La variante CUDA ocuparía ~2GB de imagen innecesariamente. La variante CPU-only es 10x más liviana y suficiente para las necesidades de embeddings del sistema.
29: 
30: ## `torchvision` y `torchaudio`
31: 
32: Estas bibliotecas auxiliares fueron removidas del Dockerfile en v1.3.0 (ver CHANGELOG). No hay imports de `torchvision` ni `torchaudio` verificados en el repositorio, por lo que su presencia solo aumentaba el tamaño de imagen sin aportar funcionalidad.
33: 
34: ## Impacto en rendimiento de embeddings
35: 
36: El procesamiento de embeddings con CPU es más lento que con GPU. Para el volumen de documentos esperado en COELSA.Intelligent, el impacto es aceptable. Si el tiempo de procesamiento se convierte en un problema, sería necesario:
37: 1. Migrar a nodos con GPU en OpenShift
38: 2. Cambiar a la variante CUDA de PyTorch
39: 3. Activar `USE_CUDA_DOCKER=true` en las variables de entorno
40:

44: - [[OpenShift]] — El entorno sin GPU donde corre la imagen
45: - [[Módulo de retrieval]] — El módulo que usa PyTorch para los embeddings

9: 
10: # Routing de modelos IA
11: 
12: ## Qué es
13: 
14: Cuando un usuario envía un mensaje, el backend debe decidir a qué endpoint enviar la request de inferencia. COELSA.Intelligent soporta dos destinos:
15: - **[[Ollama]]** nativo — endpoint Ollama en `OLLAMA_BASE_URL`
16: - **[[LiteLLM proxy]]** — proxy OpenAI-compatible en `OPENAI_API_BASE_URL`
17: 
18: ## Lógica de routing
19: 
20: ```
21: backend/server/utils/chat.py (líneas ~263–293)
22: ```
23: 
24: El routing evalúa en orden:
25: 
26: 1. **¿Tiene `urlIdx`?** → Si está definido, el modelo es proxied → usar endpoint OpenAI (LiteLLM)
27: 2. **¿`owned_by` == "ollama"?** → Usar endpoint nativo de Ollama
28: 3. **Default** → Usar endpoint OpenAI (LiteLLM)
29: 
30: ## Por qué `urlIdx` tiene prioridad
31: 
32: El campo `owned_by` no es suficiente para determinar el endpoint correcto. Los modelos con prefijo `ollama/` en LiteLLM tienen `owned_by=ollama` pero **deben** ir al proxy, no al endpoint nativo de Ollama. Si van al endpoint nativo, LiteLLM no puede procesar la respuesta y la UI muestra respuestas vacías.
33: 
34: Ver [[Validación de urlIdx]] para el detalle del bug y la corrección.
35: 
36: ## Formatos de respuesta
37: 
38: | Endpoint | Formato de respuesta |
39: |----------|---------------------|
40: | Ollama nativo | Formato Ollama propio |
41: | LiteLLM proxy | Formato OpenAI estándar (siempre) |
42:
