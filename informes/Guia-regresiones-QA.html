Framework de QA · Guía de equipo

Cómo repetir las pruebas en cada release

El equipo comparte un catálogo por aplicación. Cada release suma pruebas nuevas y vuelve a correr las aprobadas contra la versión nueva.

Dónde va cada cosa

Repo de segundos cerebros

Documentación y reglas que el agente consulta para preparar las pruebas.

Repo de regresiones

Pruebas reutilizables, con pasos, datos de prueba y resultados esperados. Una carpeta por aplicación.

Resultados de cada corrida

Informe HTML, Markdown y evidencias de lo que pasó en un build concreto.

La primera vez

Cloná el repo compartido como carpeta regresiones al lado del framework o dentro de él. Si la aplicación todavía no tiene catálogo, la primera corrida deja la base con los casos que QA aprueba para repetir.

Cada vez que sale una release

  1. Traé lo que ya existe

    Hacé pull del repo de regresiones para traer la última suite aprobada. Indicá al framework cuál es la aplicación y qué cambió en la release.

  2. Corré lo anterior y lo nuevo

    El agente prepara los casos de los cambios. El framework corre los casos guardados y los nuevos contra la misma versión de QA. Playwright ejecuta los pasos de navegador.

  3. Revisá el reporte y guardá las pruebas aprobadas

    El HTML muestra qué se ejecutó, qué falló y qué quedó pendiente. QA decide qué casos nuevos son reutilizables. El framework los incorpora al catálogo local de la aplicación.

  4. Compartí el catálogo actualizado

    Revisá el cambio, hacé commit y push en el repo de regresiones. La próxima persona recibe la suite actualizada con otro pull.

Un ejemplo

Si la aplicación tiene 100 pruebas guardadas y la release trae 5 nuevas, se pueden correr las 105 juntas. Si QA aprueba las 5 para el catálogo, la próxima release arranca con esas 105 como base.
