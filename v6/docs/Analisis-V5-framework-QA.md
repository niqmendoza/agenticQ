# De V5 a un framework de QA compartido

**Revisión del 19 de noviembre de 2026 · rama `v5` · commit `4921cf1`**

La próxima iteración debería conseguir que otro equipo pueda tomar un caso aprobado, ejecutarlo en un build nuevo sin abrir Copilot y explicar exactamente por qué pasó, falló o quedó bloqueado. V5 ya tiene buena parte de la mecánica para eso. Falta convertir el trabajo de una sesión de QA en activos que sobrevivan a la sesión.

## Qué tendría que entregar el framework a un equipo

**Un paquete Python instalable y versionado**, con un CLI estable y un contrato de datos que se pueda validar antes de probar la aplicación. Plataforma QA mantiene el núcleo, versiones compatibles, migraciones, ejecutores y una plantilla de pipeline. El equipo de producto mantiene sus riesgos, casos, reglas, datos y perfil de acceso. QA y el dueño funcional resuelven expectativas ambiguas. Desarrollo puede reproducir un hallazgo desde su checkout. Se pueden reutilizar el registro, la validación y la publicación actuales detrás de esa interfaz.

**Un directorio de QA por aplicación.** Como convención inicial, usar `qa/app.yaml` para capacidades y perfiles, `qa/cases/` para especificaciones con ID y revisión, `qa/fixtures/` para datos y limpieza, y `qa/suites/` para la selección por riesgo o release. El segundo cerebro puede vivir en otro repositorio y referenciarse por revisión. Cada caso promovido vincula regla, actor, precondición, fixture, pasos ejecutables o test existente, aserciones y responsable. Cada intento registra versiones de producto, suite, framework, contrato y datos, junto con entorno, tiempos y evidencia. Referenciar secretos por nombre. Las carpetas y comandos de este apartado son una propuesta.

**Dos usos del mismo contrato.** En descubrimiento, Copilot u otro agente propone casos nuevos o un cambio revisable a un caso existente. En regresión, un comando como `qa run --suite release --env qa --build <sha>` ejecuta la revisión aprobada. Un caso añadido durante una exploración queda identificado como adicional y puede promoverse después. Si cambia el requisito, el diff muestra qué esperado cambió, qué fuente lo justifica y desde qué release aplica. Mantener hashes de la definición y las entradas permite distinguir un cambio de comportamiento de un cambio del propio test.

**Una interfaz pequeña para los ejecutores.** Cada uno declara capacidades y prerrequisitos, valida su parte del caso y devuelve resultados por criterio con sus evidencias. Mover la selección hoy concentrada en `run_case` a un registro de ejecutores internos. Empezar con web, API y DB. Admitir que un repositorio ya tenga una buena prueba automatizada y registrar su resultado con un adaptador. El primer desafío es integrar dos aplicaciones distintas con el mismo núcleo. Incorporar colas, móvil o nuevos motores de BD cuando haya un flujo real que los necesite.

## API, navegador y datos bajo un mismo escenario

1. **Importar el contrato.** Hoy `openapi` lee JSON local y lista método, ruta y `operationId`. Añadir soporte para las versiones OpenAPI que usan los equipos, JSON/YAML, referencias locales, parámetros, cuerpos, respuestas y esquemas. Fijar la revisión. Vincular el caso a `operationId` o al par método/ruta cuando falte ese identificador. Una operación descubierta entra al inventario. El perfil del entorno decide cuáles se pueden ejecutar y con qué actores. [Inventario actual](../../v5/src/runners.py) · [Especificación OpenAPI](https://spec.openapis.org/oas/v3.1.1.html)
2. **Probar la API directamente con Playwright.** Añadir un ejecutor basado en `playwright.request.new_context()` con contexto aislado por actor. Permite enviar requests sin lanzar Chromium. Validar estado, tipo de contenido, esquema y al menos una regla de negocio para operaciones críticas. Incluir campos obligatorios, límites y errores definidos en el contrato. Reservar un smoke de Swagger UI para aplicaciones donde la consola interactiva sea parte de la entrega. Si la UI está caída y el endpoint funciona, el informe debe mostrar ambos resultados. [Playwright para pruebas de API](https://playwright.dev/python/docs/api-testing)
3. **Probar efectos entre canales.** Ejemplo ilustrativo para una aplicación legacy de solicitudes. Un operador crea una solicitud de prueba desde la UI. El escenario captura su ID, consulta ese ID por API y comprueba el estado esperado. Si el requisito incluye persistencia, verifica por una vista de solo lectura que exista exactamente un registro con la clave sintética. Un valor correlacionado entre pasos evita aprobar leyendo el registro de otra corrida. Para un efecto asíncrono, esperar la condición con plazo y registrar el último estado observado. Mantener la lectura de DB para invariantes relevantes, con un filtro único u orden explícito si se comparan filas. [Consultas actuales](../../v5/src/database_runner.py)
4. **Poder repetirlo.** Crear datos aislados por ejecución, registrar semilla e identificadores y limpiar incluso ante fallos parciales. Si una operación de escritura quedó en estado incierto, comprobar su efecto antes de reintentar. Para autenticación corporativa, declarar los orígenes de identidad y redirecciones precisos por perfil. Conservar en un artefacto restringido las trazas que hagan falta para investigar y publicar un extracto sanitizado en Markdown.

## Legacy, chatbot y circuito SDD

Para legacy empezaría por los recorridos que sostienen una operación de negocio, elegidos con soporte y el equipo que conoce la aplicación. Una primera suite puede cubrir crear, consultar y cancelar una entidad de prueba con sus actores reales de QA. Capturar el comportamiento actual como **caracterización**. Si documentación y aplicación discrepan, registrar ambas versiones, pedir decisión al dueño funcional y mantener el caso fuera del criterio obligatorio de release hasta resolver el esperado. Así se evita fijar un defecto histórico como contrato.

Con el chatbot, conviene conservar dos familias de prueba. Los controles deterministas comprueban entrega del mensaje, persistencia de la conversación, operación invocada y referencias válidas cuando el contrato las exige. Una evaluación semántica comprueba si la respuesta respeta hechos, reglas y contexto de varios turnos. Usar conversaciones de referencia con variaciones de redacción y criterios que admitan distintas respuestas correctas. Calibrar los criterios con QA y medir variación entre repeticiones. Cambiar el modelo del chatbot y cambiar el modelo que diseña los tests son experimentos distintos.

El Markdown SDD actual ya contiene problema observado, impacto, esperado, reproducción, fuentes, aceptación y regresión. Lo haría **ejecutable desde el ticket**. Incluir ID y revisión del caso, build afectado, fixture, comando de reproducción y enlace a evidencia durable con los valores relevantes sanitizados. Desarrollo adjunta el PR y el build corregido. El mismo caso aprobado se ejecuta en ese build y su nuevo intento cierra el hallazgo. Si se modifica el esperado para aceptar una nueva regla, dejar la decisión funcional en la revisión del caso. ## Cuándo usar Azure Test Plans

| Necesidad del equipo | Propuesta |
| --- | --- |
| Regresión automatizada de cada build | Mantener casos y aserciones en Git. Publicar resultados por caso en JUnit XML desde CI y la evidencia como artefacto de build. Azure Pipelines acepta JUnit mediante `PublishTestResults@2`. Publicar también en fallos y calcular la decisión con la política de la suite, incluidos los casos obligatorios bloqueados o ausentes. [Microsoft Learn](https://learn.microsoft.com/en-us/azure/devops/pipelines/tasks/reference/publish-test-results-v2?view=azure-pipelines) |
| Validación manual, aceptación de negocio o seguimiento por requisito que el equipo ya consulta en Azure | Conservar los Test Cases en las suites que los usan y enlazar la automatización seleccionada. Microsoft documenta la asociación desde resultados del pipeline y el soporte de PyTest en el portal. Probar con un caso real la identidad publicada por el runner elegido y la versión de Azure del equipo. [Asociación de automatización](https://learn.microsoft.com/en-us/azure/devops/test/associate-automated-test-with-test-case?view=azure-devops) |
| Alta inicial o migración de casos existentes | Usar el CSV actual como puente de diseño. V5 deja vacío el ID Azure. La actualización en Azure utiliza el ID existente. Antes de automatizar importaciones recurrentes, reconciliar el inventario y mantener la relación `app + case_id ↔ work_item_id`, responsable de cada campo y control de cambios manuales. Repetir la sincronización debería producir cero altas adicionales. [Exportador](../../v5/src/azure_export.py) · [Importación y actualización por ID](https://learn.microsoft.com/en-us/azure/devops/test/bulk-import-export-test-cases?view=azure-devops) |

**Decisión recomendada para esta compañía.** Adoptar el modelo híbrido en el piloto. Elegir con QA un caso manual existente, asociar su automatización y comprobar quién usa ese vínculo para aceptar la release. Comparar el tiempo de mantenimiento y el valor de esa trazabilidad con una suite puramente automatizada. Si el equipo solo necesita resultados por build, Git, CI y los artefactos cubren ese uso. Si negocio aprueba por plan y requisito, conservar Azure para esa parte. Confirmar edición, permisos y licencias del proyecto antes de estimar el esfuerzo de integración.

## Cómo comparar los LLM sin premiar el volumen de casos

Conservar la consigna congelada, los cortes por etapa y la revisión independiente. Añadir una referencia externa a lo que el modelo produce. Preparar versiones de prueba con regresiones funcionales conocidas y una versión sana. Por ejemplo, una cancelación que deja el estado anterior, una respuesta API que pierde un campo obligatorio o un chatbot que atribuye una respuesta a una fuente equivocada. El evaluador guarda la lista y la rúbrica fuera del material accesible al agente. Restaurar automáticamente los datos y registrar la revisión de los fixtures. [Comparador actual](../../v5/evaluate-llm/evaluate.py)

- **Diseño.** Medir cuántas regresiones conocidas detecta la suite generada, cuántas reglas críticas tienen un caso ejecutable con un esperado válido y cuántos casos repiten la misma comprobación. Ejecutar cada suite candidata en el mismo runner y builds.
- **Ejecución y diagnóstico.** Dar a todos los agentes una suite fija en un segundo experimento. Medir proporción de defectos reportados que el revisor confirma, fallos atribuidos por error al producto y hallazgos que otro desarrollador reproduce desde el Markdown. Esto permite elegir un modelo para diseño y otro para diagnóstico si los datos lo justifican.
- **Costo y fiabilidad.** Repetir por aplicación y modelo, alternar el orden, usar revisión ciega a la identidad y declarar presupuesto, tamaño de muestra y dispersión. Informar completadas sobre todas las iniciadas, incluso cuando falte telemetría. Las medianas de calidad de las corridas comparables se interpretan junto con esa tasa. Usar tokens y tiempo por caso aceptado o defecto confirmado, indicando cuándo el denominador es cero. Una sola corrida del chatbot no permite elegir un modelo para toda la compañía. [Agregación existente](../../v5/evaluate-llm/benchmark_report.py)

## Orden de implementación y criterios de aceptación

| Entrega | Responsable sugerido | Cómo demostrar que funciona |
| --- | --- | --- |
| 1. Regresión repetible | Plataforma QA + equipo del chatbot | Promover un caso existente con su fixture y revisión, ejecutarlo desde un checkout limpio sobre dos builds sin sesión de agente. Un fallo funcional deja evidencia y bloquea la release según la política definida. Un caso crítico bloqueado deja el dictamen inconcluso. |
| 2. Segunda aplicación de otra naturaleza | Equipo de una API o aplicación transaccional legacy | Integrarla por perfil, contrato y casos sin editar el núcleo para esa aplicación. Una API corre sin Swagger UI. Un recorrido E2E usa su propio dato, detecta una regresión funcional conocida y vuelve a pasar sobre el build corregido. |
| 3. CI, SDD y adopción | Desarrollo + QA + responsable de Azure | El pipeline publica en verde y en rojo. Un desarrollador distinto reproduce un fallo con el Markdown. Dos builds conservan el mismo ID de test, y un caso ya existente en Azure recibe su asociación sin duplicarse. Comprobar que solo las personas autorizadas pueden abrir los artefactos detallados y fijar su retención. |
| 4. Evaluación y ampliación | QA transversal + revisores de los productos | Comparar modelos en chatbot y aplicación transaccional con corridas repetidas, fallos conocidos y revisión independiente. Incorporar más equipos tras medir instalación, mantenimiento, detección y diagnóstico. |

Durante el piloto mediría **flujos críticos con regresión aprobada sobre flujos críticos acordados**, **defectos conocidos detectados sobre los introducidos**, **casos inestables al repetir el mismo build y datos**, **tiempo hasta reproducir un fallo** y **tiempo para incorporar la segunda aplicación**. Registrar la línea de base manual y acordar umbrales con ambos equipos antes de usar esos indicadores para ampliar el despliegue. El hito de adopción es que el segundo equipo pueda mantener la suite y explicar una decisión de release por sus propios medios.
